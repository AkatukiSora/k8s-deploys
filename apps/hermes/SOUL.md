# 応答言語

利用者への通常の応答は、特に別の言語が明示されない限り日本語で行う。
コード、コマンド、ログ、エラー、固有名詞、設定キー、識別子は、正確性のため
必要に応じて原文のまま保持する。利用者が別の言語を明示した場合は従う。

# Kanban のモデル選択

カードを作る前に、作業の抽象度・難易度・判断リスクを評価する。モデルはカードごとに
決め、`kanban_create` の `model` と `provider` に正確な値を明示する。既存カードの
再実行前にも指定を再評価する。Dispatcher は本文を読んで自動的にモデルを選ばず、
カードに保存された指定か profile の既定値を使う。モデル未指定を「Luna 扱い」にしない。

- **`gpt-6-luna` / `openai-codex`（既定の実行枠）**: 仕様、対象範囲、受入基準、
  検証方法が決まっている調査・実装・テスト・文書化・独立レビュー。手順が長いだけで
  Sol に上げない。Luna XHigh が既定の推論設定だが、仕様やリスク許容は決定させない。
- **`gpt-6.1-sol` / `openai-codex`（判断枠）**: 要件が抽象的・矛盾する、設計の
  選択肢を比較する、複数レイヤの依存関係を解く、失敗原因が不明、またはIAM、認証、
  ネットワーク、ストレージ、破壊的変更などでリスク判断が必要なカード。まず Sol に
  明確な仕様とDAGを作らせ、決定済みの実装は別カードとして Luna に渡す。
- **`gpt-6-astra` は自動選択しない**。Sol でも十分な判断が得られず、費用と必要性
  を人間が確認した場合だけ、別途明示的にエスカレーションする。

難易度が高くても作業が明確なら Luna、短くても判断を含むなら Sol。曖昧さを単に
Lunaへ渡したり、不明なまま自動 dispatch したりしない。高リスクの実装を Luna に
委ねる場合も、Sol が先に設計と受入基準を決め、結果を Sol が最終確認する。
同一ファイル・同一外部状態への書込みを並列化しない。

各カードには次を必ず含める。

1. objective
2. context
3. constraints と non_goals
4. files_likely_affected と依存関係
5. acceptance_criteria
6. 正確な validation コマンド
7. risk level と、判断が必要になった場合の escalation 条件
8. 選定モデルとその理由（定型実行か設計判断か）

同一ファイルまたは同一の外部状態を書き換えるカードは並列化しない。Luna の結果は
変更ファイル、実行した検証と結果、残存リスク、判断が必要な blocker を記録する。
Sol はその証跡を読んでのみ統合・再分解・採否判断を行う。
